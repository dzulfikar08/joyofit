# Internationalisation (i18n)

JoyoFit ships in Indonesian (`id`, source language and default) and English (`en`), built on **i18next** + **react-i18next**
like JoyoRogo (`joyorogo/docs/i18n.md`; same key conventions). Everything is JavaScript, so a change to copy ships over the air
(`scripts/ota.sh`, docs/ota.md): no native module is involved.

## Layout

```
src/i18n/
  locale.ts       LOCALES, LocalePref, resolveLocale(), matchLocale(), deviceLanguages()
  resources.ts    imports every JSON file; `id` types the keys, `en` must be `typeof id`
  core.ts         i18n instance (synchronous init), t(), getT(locale, ns), applyLocale(), getLocale()
  format.ts       Intl-based fmtInt/fmtDecimal/fmtDate/fmtClock/fmtDuration/fmtDistance/fmtAgo...
  native.ts       Settings choice in expo-sqlite kv-store (key joyofit.locale): initLocale(), setLocalePref()
  keys.ts         missingKeys()/orphanKeys() for tests and the check script
  locales/<locale>/<namespace>.json
  overlay.ts      Overlay type, applyOverlay(): per-platform leaves written over the base resources
  platformOverlay.ts / platformOverlay.ios.ts   null on Android and in tests; the iOS overlay on iOS (Metro picks .ios.ts)
  overlays/ios.ts, overlays/ios/<locale>/<namespace>.json   the iOS overlay (see "iOS overlay" below)
src/features/settings/LanguageSection.tsx   "Bahasa": Otomatis / Indonesia / English (Settings, Appearance)
server/src/i18n/                            Keluarga push and email text (Worker, own tiny translator)
scripts/i18n-check.ts                       key parity + hard-coded text scan, run by CI and scripts/ota.sh
```

## Which language is used

1. the "Bahasa" choice in Settings, if the user pinned Indonesia or English (stored on the device),
2. the phone's language (`Intl.DateTimeFormat().resolvedOptions().locale` on Hermes; `en-US` -> `en`, unshipped languages are skipped),
3. `id`.

"Otomatis" stores nothing, so people who never chose follow the phone, and `_layout.tsx` re-reads the phone language when the app returns to the foreground. The choice applies at once (mounted `useTranslation` components re-render, no restart).
`src/app/_layout.tsx` calls `initLocale()` before the first screen.

Dates, numbers, durations and distances go through `src/i18n/format.ts` (Intl, `id-ID` / `en-US`), never `toFixed`, `toLocaleString` or hard-coded month names.

The watch is told a language too (Huawei service `0C`, `protocol/README.md` > Language): the pinned "Bahasa" choice as `in-ID` / `en-US`, or the
phone's language for "Otomatis". `setLocalePref()` and `initLocale()` hand a pinned choice to `HuaweiWear.setWatchLanguage` (`src/features/device/watchLanguage.ts`);
the native side sends it at every connect and when it changes. A binary without that function is skipped, so this part works only in a native build that has it.

Add a namespace: create `locales/{id,en}/<ns>.json` and register it in `resources.ts`.

## Rules

- Keys are camelCase paths named after the role, never the Indonesian text: `list.empty.title`, `toast.saved`. Group by screen area.
- `useTranslation('ns')` in components (typed keys; another namespace: `useTranslation(['ns','common'])` and `t('common:actions.save')`). Outside components: `import { t } from '@/i18n'; t('ns:key')`.
- One sentence is one key with `{{params}}`; never concatenate translated fragments.
- Plurals: key suffixes with `count`. `id` has `_other` only, `en` has `_one` and `_other`.
- No translated text in module-level constants or in `useMemo` without the language in its deps (`useLocale()` from `@/i18n`).
- Indonesian: casual "kamu", no emojis. English: natural and concise. Brand and product names stay as they are.
- A literal that must stay (protocol token, debug text) gets `// i18n-ok: reason` on its line.
- Unit tests run in Indonesian (`bunfig.toml` preloads `src/i18n/testSetup.ts`); use `await applyLocale('en')` for English output.

## iOS overlay: no watch brands on iOS

App Review rejected JoyoFit twice under guideline 4.1(b) for naming Huawei and Honor without their authorization
(docs/app-store.md), so iOS shows no watch brand while Android keeps the base copy. `core.ts` initializes i18next with
`applyOverlay(resources, platformOverlay)`: on iOS the leaves of `overlays/ios/<locale>/<namespace>.json` replace the base
strings, everywhere else nothing changes.

- An overlay file mirrors the base file's nesting and holds only the replaced leaves, the same keys in `id` and `en`. It may use
  only `{{params}}` its base string uses.
- Wording: "your watch" / "jammu", "your watch's own app" / "aplikasi resmi jammu" for the vendor app, "the watch maker" /
  "pembuat jam", model lists replaced by https://fit.joyorogo.com/jam.
- Adding or editing a string that names Huawei, Honor, HarmonyOS, AppGallery or Theme Studio: add its iOS overlay in both
  locales, or, when only an Android screen shows it, give it a key path containing `android` or list it in `ANDROID_ONLY`
  in `overlay.test.ts` with the reason. That test fails on any other brand word in a string iOS can show.
- Names that come from code (catalogue model names, the name a watch or scale advertises) go through `shownName()`
  (`src/features/device/shownName.ts`), which drops a leading Huawei/Honor on iOS; iOS-only Swift texts name no brand.

## Check

```
bun scripts/i18n-check.ts          # key parity (app + server), orphans, hard-coded UI text; exit 1 on a finding
bun scripts/i18n-check.ts --list   # also lists keys never referenced
```

It is a plain script, not a `package.json` script: `scripts` is hashed into the OTA fingerprint (docs/ota.md), so adding one would change the
runtimeVersion. CI (`ci.yml`, job App) and `scripts/ota.sh` run it; `bun test ./src/` also runs `src/i18n/keys.test.ts`.

## Server text (`server/`)

Keluarga push and email use the recipient's language: JoyoRogo's internal endpoint returns each user's `locale`
(`RogoUser.locale`), the Worker maps it to `id` or `en` (anything else -> `id`) and builds the text with `serverT(locale)`.
Never keep a module-level "current language" on the Worker: it serves every language at once.

## Not translatable over the air

Text that native code builds or the OS reads from the binary needs a store build (and is therefore English only today; the iOS
Swift texts name no watch brand, see "iOS overlay"):

- iOS permission prompts (`NSBluetooth*`, `NSLocation*`, `NSHealth*UsageDescription`, photo/camera) and file type names in `app.json`;
- Android notifications posted by `modules/huawei-wear` (connection foreground service, find-my-phone, live workout, morning summary) and their channel names.

Fix when a build is due: localized `InfoPlist.strings` via a config plugin, and `strings.xml` resources (or JS-supplied text) for the Kotlin notifications.
