# Offline maps for the watch

Tools that build offline maps for Huawei watches (`offvmp` format, `<map id>.bin`) from OpenStreetMap for every Indonesian
Kabupaten/Kota, and publish them to JoyoFit's R2 bucket for the app (Settings → About & advanced → Experimental → "Offline maps on
the watch (lab test)"; protocol, findings and the pipeline's numbers in `docs/offline-maps.md`). Nothing here ships in the app.

| File | What |
|---|---|
| `regions.json` | The 514 Kabupaten/Kota: BPS code, map id, name, province, kind, Wikidata item, OSM relation, bbox (generated by `regions.py`) |
| `build-all.sh` → `build_all.py` | Builds every region (or some) from the Geofabrik Indonesia extract: resumable, parallel, splits big regions |
| `build-map.sh` | Builds one map from a bbox or polygon (the lab's first maps) |
| `publish.py` | Uploads changed maps to R2 `joyofit-maps/watch/` and rewrites `watch/catalog.json` |
| `regions.py`, `mapinfo.py`, `lib.sh` | Region list and boundaries; `offvmp` header and catalog entry; pinned converter, Python env, extract download |

`.cache/` (converter, venv, extract) and `out/` (maps, state, reports) are git-ignored.

## Setup

Tested on macOS 26 (arm64) with osmium-tool 1.19.1, Python 3.14, shapely 2.2.0, bun 1.4.3, wrangler 4.151.0, and in CI on Ubuntu 24.04
with osmium-tool 1.16.0 and Python 3.12.3 (below). The full build is meant for the owner's Linux box. On Ubuntu 24.04 / Debian 12:

```
sudo apt install osmium-tool python3 python3-venv git curl     # osmium-tool 1.16 (Ubuntu 24.04) / 1.15 (Debian 12) is fine
curl -fsSL https://bun.sh/install | bash                         # bun, for wrangler (publish.py)
git clone https://github.com/dzulfikar08/joyofit.git && cd joyofit
(cd server && bun install)                                       # wrangler 4.x
(cd server && bunx wrangler login)                               # or export CLOUDFLARE_API_TOKEN=<token with R2 edit on the account>
```

No Java is needed: the converter is Python (standard library only). `build-all.sh` and `build-map.sh` set up the rest on first use, in
`.cache/`: HDataResearch cloned at the pinned commit `c736a1a`, a virtualenv with `shapely==2.2.0`, the Geofabrik extract.

Resources for the full run: **disk** about 2 GB for the extract, the finished maps (see `docs/offline-maps.md` for the total) and up to
1-2 GB of temporary GeoJSON per running job; **RAM** about 2 GB for each `osmium extract` pass of 16 regions and up to 2.5 GB per
conversion of a dense region (Kabupaten Sidoarjo peaked at 2.4 GB), so `--jobs` ≈ (RAM in GB − 2) / 2.5.

## All regions

```
tools/offline-maps/build-all.sh --jobs 6          # every region; ask Geofabrik for a newer extract first
tools/offline-maps/publish.py --all               # upload what changed, then the catalog
curl -s https://api.fit.joyorogo.com/v1/maps | jq length
```

What `build-all.sh` does:

1. Downloads https://download.geofabrik.de/asia/indonesia-latest.osm.pbf (1.7 GB) once into `.cache/`, and on later runs only when
   Geofabrik has a newer one (conditional GET; `--no-refresh` skips the check, `--pbf FILE` uses another file). One download per run,
   never per region.
2. Reads the extract's date (`osmosis_replication_timestamp`) and skips every region whose `out/state/<code>.json` names the same date
   and recipe (converter commit, zooms, languages, buffer, size cap) and whose files are all there; `--force` rebuilds. So a run that
   stopped halfway resumes where it stopped, and a second run on the same extract does nothing.
3. Takes each region's boundary from the same extract (the OSM relation in `regions.json`, `boundary=administrative` `admin_level=5`),
   adds `--buffer-km` (1 km), simplifies it to about 200 m and writes an Osmosis `.poly`. A relation osmium cannot assemble into an area
   (Kabupaten Nunukan, whose border with Malaysia is incomplete in the extract) falls back to the box around its members.
4. Cuts `--batch` (16) regions per pass over the extract (`osmium extract --strategy complete_ways --config`), while the previous batch
   converts.
5. Converts `--jobs` regions at once: the converter's `extract_geojson.sh`, then `build_country.py` with zooms 10/12/14/16, labels
   Indonesian (language id `0x20`) then English, the region's name in the header. Header version = build time `YYMMDDHH`.
6. Size cap: if a region's cut is above `--split-pbf-mib` (40) or its map above `--max-mib` (64, the app's lab limit while the upload
   holds the file in memory), it is cut in two across the longer side of its box, and again, up to `--max-depth` (4) times. Parts get
   ids `2·10^18 + part·10^4 + code` and names "Kabupaten X 1/3" (written into the header too). A part still above the cap is flagged
   `oversize` in the report and `publish.py` leaves it out.
7. Writes `out/<id>.bin`, `out/<id>.json` (catalog entry: id, code, name, province, kind, part, bbox, size, SHA-256, version, builtAt,
   osmDate), `out/state/<code>.json`, and `out/report.json` (counts, failures, oversize parts, total bytes, the 15 largest regions).
   Exit code 1 when a region failed; the others are kept and the next run retries the failed ones.

Some regions only: `--only 3573,3515,3579` (BPS codes) or `--province "Jawa Timur"`. Cuts and logs stay in `out/work/<code>/` with
`--keep-work`.

Smoke test (2026-10-26, on the Mac: 8 GB, 8 cores; Geofabrik Indonesia of 2026-10-25T21:21:21Z), `--only 3573,3515,3579 --jobs 3`: 117 s
in all (19 s boundaries, 35 s cutting, the rest converting); Kota Batu 2.2 MiB in 8 s, Kota Malang 7.1 MiB in 26 s, Kabupaten Sidoarjo
21.1 MiB in 71 s; peak RSS 2.4 GB. A second run skipped all three in 0.3 s. The split path was checked with `--max-mib 3
--split-pbf-mib 5` on Kota Malang: 3 parts of 2.2 to 2.6 MiB, ids `2000000000000013573` to `…033573`, headers "Kota Malang 1/3" to "3/3".
On Linux, `.github/workflows/offline-maps.yml` builds Kota Ambon (8171) from Geofabrik's Maluku extract on every pull request that touches
this folder (Ubuntu 24.04, osmium 1.16.0, Python 3.12.3: 14.1 MiB in 36 s) and checks that a second run skips it.

Expected for all 514 regions (from cutting every region on 2026-10-25, see `docs/offline-maps.md`, "Size, time and cost"): about 2.0 to
2.6 GiB of maps, about 2 to 2.5 CPU hours, so 40 to 60 minutes with `--jobs 6`.

### Monthly refresh

Two ways; use one. **GitHub Actions**: the same workflow's `monthly` job rebuilds everything on the 2nd of each month (about 1 to 1.5 hours
on the 4-CPU runner, inside the 6-hour limit) and publishes when the repository secret `CLOUDFLARE_R2_TOKEN` (an API token with "Workers R2
Storage: Edit" on the JoyoFit account) is set; "Run workflow" with "full" starts it by hand. **The owner's Linux box**, where `out/` persists
(a stopped run resumes there), with a systemd timer. `~/.config/systemd/user/joyofit-maps.service`:

```
[Unit]
Description=JoyoFit offline watch maps: rebuild and publish
[Service]
Type=oneshot
WorkingDirectory=%h/joyofit
Environment=PATH=%h/.bun/bin:/usr/local/bin:/usr/bin:/bin
# Put CLOUDFLARE_API_TOKEN=… (R2 edit on the JoyoFit account) in this file, mode 600.
EnvironmentFile=%h/.config/joyofit-maps.env
ExecStartPre=/usr/bin/git pull --ff-only
ExecStart=/bin/sh -c 'tools/offline-maps/build-all.sh --jobs 6; tools/offline-maps/publish.py --all'
Nice=10
```

`~/.config/systemd/user/joyofit-maps.timer`:

```
[Unit]
Description=JoyoFit offline watch maps, monthly
[Timer]
OnCalendar=*-*-03 02:00
Persistent=true
[Install]
WantedBy=timers.target
```

```
systemctl --user daemon-reload && systemctl --user enable --now joyofit-maps.timer
loginctl enable-linger "$USER"                    # run while nobody is logged in
journalctl --user -u joyofit-maps -f              # watch a run; out/report.json has the summary
```

`publish.py --all` publishes whatever regions are built, also after a run with failures (it skips only oversize parts).

## Publishing (what the app downloads)

```
tools/offline-maps/publish.py --all                         # every region build-all.sh finished
tools/offline-maps/publish.py 2000000000000003573           # single maps, e.g. from build-map.sh
tools/offline-maps/publish.py --all --dry-run               # what would change; writes out/catalog.json only
```

`publish.py` reads `watch/catalog.json` from the R2 bucket `joyofit-maps` (`bunx wrangler r2 object … --remote` from `server/`, account
`b7e6f845…`), uploads every `out/<id>.bin` whose SHA-256 differs from the catalog's, writes the new catalog last (so it never lists a
file that is not there yet) and then deletes the files of maps that left it (a region split differently than before). Entries of
JoyoFit ids that lack code/province/kind (maps from `build-map.sh`) get them from `regions.json`. JoyoFit's Worker serves the catalog at
`GET /v1/maps` (filters `province`, `q`, `near`, `limit`; `server/src/maps.ts`) and the files at `GET /v1/maps/<id>.bin`; the app
downloads from there and checks size and SHA-256 before it keeps a file. The bucket also holds the bike computer's PMTiles
(`docs/bike-computer.md`); this only writes under `watch/`.

## The region list

```
.cache/venv/bin/python tools/offline-maps/regions.py generate --pbf tools/offline-maps/.cache/asia_indonesia-latest.osm.pbf
```

(after one `build-all.sh` run has created the venv and the extract). It asks Wikidata (CC0) for every item with a 4-digit "Statistics
Indonesia area code" (P1588, the BPS kode wilayah), its Indonesian label, its OSM relation (P402) and its province (P131, a "province of
Indonesia"), then matches the extract's `admin_level=5` relations by id or `wikidata` tag. 2026-10-26: 514 regions (416 kabupaten, 98
kota) in 38 provinces, all with a boundary; warnings for Kabupaten Ciamis (no Indonesian label on Wikidata; OSM's name used) and Kabupaten
Nunukan (box fallback, above). Wikidata keeps the BPS codes from before the 2022 Papua split (91xx Papua Barat, 94xx Papua) with the new
provinces as P131, so the ids of Papua's regions stay stable; a region created later needs a new run and a review of the diff. The list
changes rarely: regenerate it when BPS adds a region, not monthly.

## Map ids

The watch takes the map id from the file name only (`<id>.bin`, `<id>_contour.bin`, `global.bin`). Huawei's ids come from Huawei's
map server; the 2,275 ids listed in HDataResearch's `offvmp/docs/filenames.md` are all below 2^60 (1,152,921,504,606,846,976) and look
random. JoyoFit's ids are **2,000,000,000,000,000,000 + part · 10,000 + the BPS region code** (part 0 = the whole region; 1 to 16 for the
parts of a split one): above 2^60, so they cannot collide with a Huawei id, still below 2^63 (a signed 64-bit long), and readable. The
Fit 4 Pro accepted and drew `2000000000000003573` and `2000000000000003578` (docs/offline-maps.md, "Results").

## One map

```
tools/offline-maps/build-map.sh --region asia/indonesia/java --bbox 112.57,-7.37,112.87,-7.17 \
    --id 2000000000000003578 --name "Surabaya (lab)"
# → out/2000000000000003578.bin and .json; --poly FILE cuts with a polygon instead of the bbox
```
